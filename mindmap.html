How the signatureCipher solver works

One idea: run YouTube's own player and ask it. Never re-implement the transform.

signatureCipher solver Node · no dependencies · no network calls to get a player response

1 Input — what a signatureCipher is data

s=g%3DgpLpgLHd4Q3… sp=sig url=…videoplayback?…&n=…
  • s — encrypted signature (106 chars here)
  • sp — name to write the answer back as (sig)
  • url — real stream URL, carrying the throttle token n
  • As-is the URL is useless: googlevideo answers 403

2 Clean — cleanCipher() solver.js

  • "s=…&url=…", — quoted JSON string + comma
  • "s=…&url=…" — bare JSON string
  • { "itag":137, "signatureCipher":"…" } — one format
  • { "streamingData": … } — whole playerResponse
Last bug: a leading " made the parser see raw s len 0 → nothing signed → 403 everywhere.

3 Sandbox — fake browser tools/sandbox.js

  • DOM: every element method is a no-op
  • network: fetch rejects — player cannot phone home
  • timers: wrapped in try/catch (player reports errors via setTimeout(() => { throw }))
  • intrinsics: not injected from Node — the context keeps its own String/Array
  • then vm.createContext(sandbox)
  • result: a real JS global environment, isolated from ours

4 Load the player vm-solve.js

  • base.js is one IIFE: (function(g){ … })(_yt_player)
  • Kh, Gh, ti are closure-local — invisible outside
  • inject one line inside the IIFE, just before the tail:
    g.__api = { rk, Kh, Gh, Nh, ti, Se };
  • run once → _yt_player.__api exposes them; cached for the process
Cost: ~150–240 ms to parse 2.5 MB, once. Every later solve is microseconds.

5 Solve the signature — exactly what the player does Gh · Kh

sig = Gh(21, 2482, Kh(41, 790, s))
  • Kh(41,790,·) — legacy decode stage → identity in this build (verified 200/200)
  • 21, 2482 are not payload: d = 2482 ^ 21 = 2471 selects a path and obfuscates indexes
  • then 8 array ops, args = d ^ constant taken from the source
OE 1swap [0] with [1]
VJreverse
OE 53swap [0] with [53]
OE 9swap [0] with [9]
VJreverse
dD 3drop first 3
VJreverse
dD 3drop first 3
106 chars in→ 100 chars out AE0s2JYwRAIgFmNRAdOsZ9A4…
Re-implemented those 8 lines by hand and compared with the player on 200 random inputs: 200/200 identical. We still call the player, because the constants change every build.

6 Solve n — the throttle token g.ti · Gh · Se

new g.ti(url, true).get("n") → Gh(1, 8224) → Se(40, 1447)
  • get('n') runs Gh(1,8224,this); with a=1 the signature branch is skipped
  • its other branch fires: Se(40,1447,urlObject) re-parses and rewrites n in place
  • inner pipeline: Lh(16,7356)×43 → Nh(6,1842) → Gh(10,8235) → Kh…
  • we never re-implement it — hand over a URL, take the answer
n raw · 19 chars · 403 → n solved · 14 chars · 206

7 Rebuild the URL output

…&n=qnHT6bGs… → …&n=150bcioiBR8MZg&sig=AE0s2JYw…
  • s is dropped; the solved value is written as sig
  • verified: identical to the player's own rk(url,"sig",s) output
  • the only difference is a cosmetic alr=yes that rk adds

9 Play — and get out of the way server · page

  • play.html plays the direct URL; falls back to local /stream (Range-aware proxy)
  • page holds EventSource('/events'); closing the tab drops it
  • server exits ~3 s later → nothing left running
